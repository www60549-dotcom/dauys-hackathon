# Запуск Dauys для защиты

## На этом компьютере

`./stop-local.ps1`, затем `./start-local.ps1 -DemoMode $false`.
Для телефона: `./start-local.ps1 -DemoMode $false -Lan`, одна Wi-Fi сеть,
адрес `http://<LAN-IP>:8080` (готовая production-сборка) или `:5175` (Vite).
QR автоматически использует найденный LAN-адрес на порту 8080.
После аварийного завершения среды скрипт ждёт восстановления PostgreSQL до минуты.
Телефон должен войти сотрудником; никакого обхода авторизации в QR нет.
Локальный HTTP не даёт всех возможностей микрофона/clipboard: для них нужен HTTPS.

## Linux / Docker Compose

1. Скопировать `.env.example` в `.env`, задать случайные POSTGRES_PASSWORD и
   DEMO_PASSWORD. Для URL подключения использовать hex-пароль без спецсимволов.
2. На свежей демонстрационной БД оставить DEMO_MODE=true; при повторном старте
   существующие пользователи не меняются. Для компании DEMO_MODE=false.
3. `docker compose up -d --build`; открыть `http://127.0.0.1:8088`.
4. `docker compose logs --tail=100 api` и `curl http://127.0.0.1:8088/api/health`.
5. Для LAN задать WEB_BIND=0.0.0.0 и добавить реальный LAN origin в APP_ORIGINS.

Nginx отдаёт React и проксирует /api на одном порту. PostgreSQL и API не публикуют
свои порты. SSE buffering выключен, тайм-аут proxy больше жизни потока.
Для публичного production нужны HTTPS termination, COOKIE_SECURE=true и точный
APP_ORIGINS. Локальные файлы и PostgreSQL находятся в отдельных named volumes.

## Бесплатное демо: Render + Vercel

Render: импортировать репозиторий с `render.yaml` как Blueprint. Создаются только
free web service и free PostgreSQL. Root Dockerfile собирает React и Go; backend
может также раздавать весь сайт самостоятельно. Вложения на free web service
эфемерны; PostgreSQL free ограничен сроком 30 дней; сервис засыпает при простое.
Это временный стенд для хакатона. Перед защитой открыть health и проверить вход,
а после защиты сохранить нужные данные. Резервную копию рабочей БД не публиковать.

У сервисного окружения задать APP_ORIGINS с точными HTTPS-адресами Render и Vercel.
Сгенерированный DEMO_PASSWORD взять в Render environment; три demo email описаны
в README. Это отдельный демо-датасет, а не перенос реальных локальных обращений.

После готовности публичного API:

Проект Vercel уже связан с репозиторием. До появления API автодеплой отключён,
попытка ручной сборки завершится понятной ошибкой конфигурации. Следующая команда
создаёт готовый rewrite и заменяет подготовительную конфигурацию.

```powershell
node scripts/prepare-vercel.mjs https://your-api.onrender.com
npx vercel@latest --prod --yes
```

Скрипт создаёт vercel.json: /api проксируется на Go, остальные маршруты — SPA.
Куки HttpOnly остаются same-origin, COOKIE_SECURE=true. API responses не кешируются.
После публикации проверить login, создание, загрузку/скачивание файла и SSE через
сам Vercel origin. Не считать успешной публикацией одну только страницу входа.

## Резервное копирование и восстановление

`./scripts/backup-compose.ps1` делает согласованную пару database.dump + uploads.tar.gz
с SHA256. На время копирования API останавливается, PostgreSQL остаётся доступен;
скрипт снова запускает API даже при ошибке копирования.

Восстановление сначала проверять в отдельном Compose project (`-p dauys-restore`)
с другим WEB_PORT и новыми volumes. Создать пустую БД; остановить её API, передать
dump через `docker compose cp`, запустить `pg_restore --no-owner -U dauys -d dauys`.
Скопировать архив uploads и распаковать в /data отдельного API-контейнера.
Проверить health, количество обращений, вход и доступность файлов, затем запускать API.
Не использовать `down -v` для рабочего проекта и не восстанавливать поверх
единственной рабочей БД. Переключение на восстановленный стенд выполняется после проверки.

## Сценарий показа (5 минут)

1. Гость → минимальный вход сотрудника → новая проблема → ответственный.
2. Исполнитель запрашивает уточнение; сотрудник видит обновление и отвечает.
3. Пилот: baseline → цель → запуск → фактическое измерение → вывод.
4. Решение исполнителя → подтверждение автора → подтверждённый эффект.
5. Показать отдельный мотивированный отказ и возврат повторившейся проблемы.
6. Аналитика: поступления по созданию, решения по событиям, прогноз отдельно.
7. QR с публичным адресом: открыть форму на телефоне, отправить обращение,
   проверить его с другой сессии через SSE.
