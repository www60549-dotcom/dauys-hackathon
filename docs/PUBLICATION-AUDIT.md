конфигурациями и документацией публикации. Код, дизайн и бизнес-логика не менялись.

- Репозиторий: https://github.com/www60549-dotcom/dauys-hackathon

- Удалённый main на момент аудита совпадает с этим HEAD; других удалённых веток
  или тегов git ls-remote не показал. История не shallow.
- Репозиторий уже был опубликован до этой проверки. Во время этой задачи не
  выполнялись commit, push, смена ветки, переписывание истории или новая публикация.
- Подготовленные изменения пока не входят в HEAD. После подтверждения нужен
  новый локальный коммит и получение его полного SHA. Текущий HEAD не выдаётся
  за финальный коммит с этими изменениями.

## Фактическая проверка секретов

- Gitleaks 8.30.1 загружен из официального GitHub release; SHA256 архива проверен
  по опубликованному checksums-файлу. Использована стандартная конфигурация,
  без allowlist, baseline или подавления находок комментариями.
- Проверены все 11 доступных коммитов всех refs: `git --all --full-history`.
  Результат: 0 находок Gitleaks; объём diff около 1,84 МБ.
- Проверена копия текущих 316 отслеживаемых файлов: 0 находок Gitleaks.
  После подготовки повторно проверены также новые документы и изменённые файлы.
- Дополнительно просмотрены 411 уникальных Git blob-объектов из refs/reflog и
  доступных unreachable-объектов: сравнение с локальным секретным значением,
  поиск заголовков приватных ключей и проверка ссылок на credentials/DATABASE_URL.
  410 объектов текстовые, один бинарный. Приватных ключей и совпадений с локальным
  секретом не найдено. Публичные URL без пароля и подстановка переменных не
  считаются утечкой реальной строки подключения.
- Найдены два env-файла: отслеживаемый безопасный `.env.example` и игнорируемый
  `.env.local`. Второй содержит имя переменной VERCEL_OIDC_TOKEN; значение в отчёт
  не записывалось. Точного совпадения этого значения в Git-объектах нет.
- `.env`, `.env.local`, `.env.production`, папки data, .vercel и приватные ключи
  не отслеживаются; в истории по этим путям файлов с секретами не найдено.
- Supabase, service_role и JWT-секреты в реализации не используются: здесь Go API
  с серверными cookie-сессиями. StreamKit в исходниках не найден.
- Это проверка известных форматов и доступной истории, а не гарантия отсутствия
  любого возможного секрета. Недоступные/ранее удалённые удалённые refs и сторонние
  форки в охват не входят. Рабочие локальные настройки сохранены.

## Обнаруженные риски и исправления

1. В исходниках, тестах, CI и legacy Compose есть общедоступные demo/test пароли.
   Они намеренно синтетические; реальные облачные ключи или production DSN не
   обнаружены. Эти пароли запрещено использовать в публичной/корпоративной среде.
   Если какое-либо такое значение ранее повторно использовали для реального сервиса,
   его нужно заменить там; удаление строки из нового коммита не очистит историю.
2. Старый `.gitignore` защищал env/data, но не отдельные ключи, credentials-файлы
   и дампы вне data. Добавлены соответствующие правила. Миграции и исходники
   остаются отслеживаемыми, `.env.example` разрешён явным исключением.
   Проверены 29 разрешённых/исключённых путей: все проверки прошли.
3. `.env.example` существовал, но отражал в основном Compose. Он дополнен
   переменными прямого API, QR, Vite proxy и локального запуска; секретные поля
   пусты, остальные значения безопасные. Разделено, какие инструменты читают .env,
   а каким требуется окружение процесса.
4. README дополнен установкой на новом компьютере, списком переменных, режимом
   seed и указанием выбора собственного DEMO_PASSWORD. Фактические функции и
   ограничения вынесены в FEATURES.md.

Реальных опубликованных приватных credentials не обнаружено; основания для
переписывания истории по результатам этой проверки нет. Ничего не отзывалось
и история не переписывалась. При обнаружении реального секрета публикацию
следует остановить, отозвать/заменить credential и отдельно согласовать очистку
истории и всех затронутых refs. Один новый коммит старый секрет не удаляет.

  не входят в исходники. .dockerignore / .vercelignore исключают их из контекстов.

## Следующие действия

1. Просмотреть полный diff и подтвердить создание локального коммита.
2. Создать коммит только после подтверждения, выполнить `git rev-parse HEAD`.
3. Отдельно разрешить push, если организаторы должны получить именно новую версию.
4. В Google-форме указать URL репозитория и SHA коммита, реально доступного на GitHub.
   Локальный, ещё не отправленный SHA организаторы получить не смогут.
5. Если нужна публичная рабочая ссылка, отдельно завершить размещение API/БД и Vercel;
   исходники уже доступны, облачный стенд этим аудитом не создавался.

Локальные redacted JSON-результаты и инструмент лежат в игнорируемой
data/submission-audit/. Они не должны отправляться вместе с реальными env,
дампами БД, Vercel credentials или uploads. Архив исходников ранее создан из Git;
после будущего финального коммита его можно пересобрать через git archive.
